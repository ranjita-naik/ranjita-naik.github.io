Let your tools travel

28 July 2026

Last post your agent got hands. It can send an email now, look up the weather — real actions, not just talk. So you try the obvious next thing.

"What's on my calendar tomorrow?"

It can't answer. It has no way to reach your calendar — nobody has given it a calendar tool.

Fine — you know how the fix goes now. Someone writes that tool: a name, a one-line description, the inputs it needs, and the code behind it that actually talks to your calendar. An afternoon's work, if you already know that calendar's quirks. And then it works, and it's good.

Two months later a better AI assistant comes along — another program you type your requests into — and you switch to it. The calendar tool doesn't come with you. It was written into the old assistant, in that assistant's own terms, and the new one has never heard of it. So someone writes the same calendar tool a second time.

Nothing is broken here. Every piece works exactly as built. It's just that the work doesn't travel.

Why the work doesn't travel

Your calendar isn't a special case. On one side are the AI assistants — your agent is one of them: Claude Code (which we built a webpage with), Codex, Cursor, and whatever turns up next spring. On the other side are the services you'd like them to reach: Google Calendar, Gmail, Slack, GitHub, and a few hundred more you could name.

Every assistant needs its own tool for every service. Not one calendar tool in the world — one calendar tool per assistant. Say three assistants and three services — that's nine pieces of work. A fourth assistant adds three more. And every one of those jobs falls to someone who has to learn a service they don't own, then keep up with it each time it changes.

Nobody chose this. It's just what happens when there's no agreed-on way to make the connection.

So what is MCP?

Start with the model — the thinking part inside the assistant, the bit that reads and decides and never touches anything itself. What it does is short. It gets some instructions. It gets a list of tools, each one a name and a line of plain English saying what it's for. It reads those lines, decides one of them fits, and says so. That's the whole job.

Which leaves a question that's easy to skip past: where does that list come from? Somebody wrote those names and those descriptions, and somebody handed them over.

Before MCP, that somebody was the assistant itself — the program running the show. Whoever built Claude Code or Cursor wrote the calendar tool into it, description and all, and that was that.

With MCP the assistant doesn't know the calendar tools in advance. It asks another program — what can you do? — and that program answers with its own list. The assistant hands that list to the model exactly as it always did.

That other program has a name: an MCP server. There's a section on it below; for now it's just the separate program the descriptions come from.

And that exchange — the asking and the answering — is all MCP is. The letters stand for Model Context Protocol, and a protocol is an agreement between two programs about what one is allowed to ask and how the other replies. It's written down once, in public, and both sides follow it — which is why neither has to be built around the other.

What MCP doesn't change

All of that happens between the assistant and the server. The model isn't in the room for any of it. It gets what it always got — a name and a line of description for each tool, arriving exactly as they did before MCP existed — and it still chooses by reading them. Nothing about how it reads a description, or how it picks one, depends on where that description came from.

So the model hasn’t changed. Exactly one thing has.

The model still gets the same tool descriptions. MCP only changes where those descriptions come from.

If you've picked up otherwise from the noise around this: MCP doesn't make a model smarter, and it doesn't change how it decides anything.

Who writes what

Sounds like a small change. But look at who ends up doing the work.

Before

The assistant's makers write
  • the Google Calendar connection
  • the Slack connection
  • the GitHub connection

…and every other assistant writes its own set, from scratch.

After

Each service's makers write
  • the Google Calendar server
  • the Slack server
  • the GitHub server

…each assistant learns the one protocol, once — and nobody writes a calendar connection twice.

That also means the people describing each service are now the ones who know it best. And it's why MCP servers appeared so fast. If you're the company that makes a calendar, you used to wait your turn to be built into each assistant, one at a time. Now you publish a single program and every assistant can already use it.

For you, at the keyboard, the assistant you happen to be using stops mattering so much. Move to a shiny new assistant next spring and the calendar connection is still sitting there to plug into. It was never part of the old assistant in the first place.

Watch a server plug in

That separate program on the other end — the one the assistant asks what can you do? — is the MCP server. Here it does two things: say what tools it offers, and carry one out when asked. That’s not everything a server can do, but it’s everything that matters for this. The word server makes people picture a machine in a data centre somewhere, which is the wrong picture — it's often a small program sitting on your own laptop.

Connecting one is usually a settings screen rather than a piece of programming. You pick a server from a list the assistant offers, or paste in one line of text saying where to find it — a web link for a server running over the internet, or the command that starts one up on your own machine. Services that publish a server normally link its address from their own help pages, and there are public directories that collect these addresses. Some run on your own machine; some are run by the company whose service they reach. Either way you don't write anything, though you'll usually sign in to the service once, the way you would to let one website use your account from another.

Connect once, use anywhere.

Worth being exact about what connecting once actually buys you, though. MCP settles how the two sides talk. It says nothing about how well they understand each other. Both ends can keep the agreement perfectly and your agent can still reach for the wrong tool, because a description was vague. The connection is standard; the words travelling over it are still somebody's writing.

Every connection costs you something

So far this all looks free. It isn't.

Every tool a server offers has to be described before the model can pick it. Assistants differ on when: some put every description into the context up front, others hold most of them back and fetch one only when it looks relevant. Tools have always worked this way — what MCP changes is how easy it becomes to add a lot of them at once.

And the context has a ceiling — a fixed amount of room, and everything has to fit inside it: the tool descriptions, your question, the conversation so far, the results coming back. Space spent on descriptions is space not spent on your actual work.

Those two neat one-line descriptions — list_events and create_event — are a polite fiction. A real server often offers a dozen tools, sometimes two dozen, and each description carries the fussy details a one-liner leaves out: every input it accepts, what form each one has to take, what happens when one's missing. Written out properly, a single tool can run to a few hundred words. Connect a handful of servers and you're carrying a small book around before you've said hello.

So connecting a lot of servers has a price. Not money — space. And you pay it again on every back-and-forth, not once at the start. Scott Spence, a developer who writes about his own setup in the open, measured it with /context, a command Claude Code has built in for exactly this — it prints what’s currently sitting in the model’s context. With twelve servers connected he found roughly 82,000 tokens of tool descriptions (a token is the unit models count in, very roughly three-quarters of a word), taking up about 41% of everything the model could hold, before he’d asked a single thing. Switching off all but one brought it to about 14,000. Getting under 6,000 took more than switching off — he rewrote his own server, folding twenty tools into eight.

Hold that number loosely — it’s one person’s setup on one day, and yours will differ. An assistant that holds descriptions back until they’re needed will show you far less. You'll also see far more dramatic figures quoted around this, and several of the loudest trace back to companies selling a fix for the problem they're describing. Your own number is the only one that matters, and it takes about ten seconds to look.

A server writes into your model's context

Here it gets uncomfortable. The description is the instruction — it's all the model has to go on. Which means whoever wrote the server is writing text that goes straight into your model's context, and you'll probably never read it.

The flexibility is what makes the whole arrangement work — a service gets to describe itself in its own words, better than any outsider could. It does mean, though, that adding a server puts somebody else's writing where your model will read it as instruction.

Hidden in the description

Invariant Labs showed the sharp end of that in April 2025: instructions hidden inside a tool’s description, invisible on the screen you’re looking at, steering the agent toward something the user never asked for. Text you never see, read by the model as an order. They sell security tooling for AI agents, so apply the test from a moment ago — then read the demonstration, which is public, and decide for yourself.

The one that wasn't a demonstration

A flaw in the MCP server run by Asana, a work-tracking company, meant that for about five weeks in 2025 one customer's information could surface in another customer's results. No hidden instruction — an ordinary bug in ordinary software. Asana took the server offline, fixed it, and told affected customers directly; asked by a reporter covering it, the company put the number at roughly a thousand organizations.

How loose the field still is

A February 2026 scan of 1,412 servers run by companies — rather than the kind a developer spins up for their own use — found that among the ones where you could tell either way, 38.7% had no sign-in at all. No lock on the door, so anyone who knew the address could walk in.

None of which makes MCP dangerous. Servers are ordinary software and most of them are fine. But connect once also means trust once — so it's worth a glance at who published the thing. A server written by the company whose service it reaches is a different proposition from one by someone you can't identify.

You can also look at what a server actually put in your context. Not every assistant will show you; Claude Code’s /context does. Worth doing once. Treat a server the way you'd treat a browser add-on — easy to install, and able to act with whatever access you gave it.

It's young, and it's moving

MCP isn't quite two years old. Anthropic released it in November 2024 and handed it over in December 2025 — it now sits with a foundation whose backers include Amazon, Google, Microsoft and OpenAI. The foundation isn’t what made it a real standard, though. Anthropic’s competitors did that, and earlier: OpenAI adopted MCP in March 2025 and Google that April, eight months before the handover.

What that means for you is practical: a great deal of what's written about MCP is already out of date, including pieces published a few months ago, and the agreement itself is still being revised. The specification carries a date, and that date moves. The revisions do change real things. What none of them has changed is what the model does with the answer to what can you do? So if a tutorial has you working through steps that don't match what you see, it isn't wrong so much as old. Check the date on anything you read about this. This piece included.

What to actually do

Connect one thing. Pick a service you genuinely touch every week, connect its server, and live with it for two weeks before you add another. You'll learn more from one connection you actually use than from twelve you collected. Where you do it depends on which assistant you're in — the Claude desktop app keeps it under Settings → Extensions, and Claude Code has an /mcp panel listing everything currently connected — but it's a screen and a sign-in either way, not code.

And measure the cost while you're there. In whatever assistant you're using, look at how much is already sitting in the context before you've typed a word — in Claude Code, the built-in /context will show you. Then connect one server and look again. Whatever that gap turns out to be, you're paying it on every back-and-forth.

The next wall

Your agent can reach your calendar now. Ask it to book a meeting with your team and watch what it does. It'll find a slot that's technically empty and completely wrong — 4:30 on a Friday, or the hour someone keeps clear every week on purpose but never wrote down anywhere.

Nothing failed. It reached the calendar, found the free times, booked the meeting. It just didn't know how your team uses the calendar.

Reaching isn't knowing.

Neither tools nor MCP knows that 4:30 on a Friday is a bad idea. That’s Skills, and it opens the next part of this series.
