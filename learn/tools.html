Give your agent hands

24 July 2026

Yesterday your agent learned to remember you. A real step — but look at what it still can't do. Ask it to check your code on GitHub (where a lot of people keep their projects online), glance at your calendar, or read a page that's live on the web this second, and it comes up empty. Same three walls we left it staring at last time. Its memory got better; its reach didn't.

This is what people are really pointing at when they say an AI "can't do anything." It can think brilliantly and still not lift a finger.

Thinking isn't doing.

So today is about giving it hands — and the small, surprising thing that makes them work.

You've already seen this work

Here's the reassuring part: you've watched an agent do things before. When you built that webpage by describing it, the agent wrote a file, changed it, and checked its own work — three real actions, done for you. That's what it looks like when an agent has hands. And those hands have a name: they're called tools. Each of those three actions was one. They even have their own names — Write, Edit, and one called Bash — but the names don't matter yet. What matters is you've already watched tools work. You just never saw them called that.

WriteEditBash

A tool, in three parts

Three plain parts: a name, a one-line description of what it does, and the inputs it needs. That's the core of it. Here's one:

send_email
What it does: sends an email for you.
Needs: who it's to, a subject, and the message.

A real tool definition usually carries a little more than this — the type each input should be, which ones are required, roughly what it hands back. I'm keeping the card simple on purpose; those three parts are what you need to understand it.

When the agent wants to act, it doesn't run the tool itself. Remember the loop: it chooses a tool and fills in the inputs, and ordinary code does the actual sending. So keep the two straight — memory changed what your agent knows; a tool gives it something it can do. (You'll also hear this called "function calling" — different name, same idea, and it works this way well beyond Claude.)

What the model actually sees

Something sneaks into the conversation that most people never picture, and it's the whole key. Say you type "email Alice I'll be ten minutes late." The model — the thinking part inside the agent — doesn't just get your sentence.

A beat before your words reach it, the software gathers up the tools it's allowed to use — each the same kind of card you just saw — and sets them in front of the model along with your request. From there, using a tool is a back-and-forth between two players: the software (the everyday program running the show) and the model (the thinking part, which only ever decides). What they build between them is the model's context — the context window from the memory post, that single scratchpad holding everything it has to work with, written out in full this time. It's easiest to picture as a single page that grows. Watch it fill up, step by step, for "Email Alice I'll be ten minutes late":

Those cards on the page are just text, remember — pasted in fresh each time. (Hold onto that; it pays off in a minute.) And since that text is the whole of what the model has to go on, the exact words you put on it start to carry more weight than you'd guess.

Which means the description does more work than you'd think

If the description is all the model has, then how you write it quietly decides whether the agent reaches for the right tool. Anthropic, who make Claude, call a tool's description "by far the most important factor" in whether tools work well. Sounds like a footnote. Watch what it actually does.

A few real cautions

In most setups, every tool's description gets handed to the model on every turn, so the more tools you pile on, the more it has to read through before it does anything — and that has a cost. (Smarter setups show the model only the tools it's likely to need, but the tug toward bloat is real.) A good description helps the agent choose well; it does not make the tool safe — a tool does exactly what its code does, no more and no less. And that's the real weight of giving an agent hands: those hands touch your actual files and your actual accounts. It's why Claude Code stops to ask before it runs Write, Edit, or Bash. Look before you let it run.

Where all this lives

If you've been following closely, one thing's still nagging: a tool is a name, a description, and some inputs — but those have to live somewhere. Two honest answers. If you're using something like Claude Code, the everyday ones come built in — reading a file, editing it, running a command are already there, nothing for you to set up. (You can even point it at a small script of your own and, in your CLAUDE.md, tell it when to reach for that.) And if you're building your own agent, you write those definitions yourself, in its code. What there isn't is one agreed-on place they live or one agreed-on way to describe them — every setup does it a little differently, and that difference is about to become the whole problem.

The next wall

Here's the thought to pick back up: because those cards are just text, handed over fresh each time, you can teach your agent something new without retraining anything — you add a card. Nothing about the model changes; you change what it's handed. That's the quiet superpower. It's also the trap. Reaching your GitHub takes one hand-built tool. Your calendar, another card. Then Slack — your team's chat. Then your notes. Then your database, the place your project's records live. Each is its own little card, wired up by hand. Switch to a different assistant next week and you start over.

That's a lot of one-off wiring. You can feel the next question coming: isn't there a standard — one universal plug — so any tool just connects, instead of being rebuilt every time?

There is. It's called MCP: one agreed-on way to plug tools in, so the same connection works no matter which assistant you're using. Not a magic supply of tools — just one agreed-on way to plug them in. That's the next post.

Try it before then: in the project you already have, ask your agent to do something that needs a tool it already has — read a file, or run a quick command — and watch which one it reaches for. (Notice it pausing to ask before it acts.) Then meet me at MCP.
